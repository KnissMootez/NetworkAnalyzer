\chapter{Moving to Cloud Inference}



\section*{Introduction}
\addcontentsline{toc}{section}{Introduction}

The previous chapter ended on a hardware ceiling: a 7B--8B model was
already too slow on a 4~GB GPU, and no local model realistic for that
hardware was going to fix it. There was, however, one thing working in
favor of moving the reasoning off-device: since the environment was
entirely synthetic from the start (Section~2.1.5), the usual objection to
sending data to a cloud-hosted model simply did not apply here — there
was no real subscriber data to protect. That removed the main reason to
keep insisting on local inference, and made the switch to a cloud-hosted
model a pragmatic next step rather than a fraught one. This chapter walks
through how that decision actually got made, and what changed once it did.

\section{The Case for Cloud Inference}

Somewhere in the middle of babysitting local qwen3:8b through yet another
sluggish response — close to five minutes for a single prompt to come
back — the whole thing stopped feeling like an engineering trade-off and
started feeling like a bad idea. Both GPU and CPU were pinned the entire
time, since the model did not fit cleanly into 4~GB of VRAM and spilled
over onto the CPU, which raised a more immediate concern than ``is this
the right architecture'': at this rate, was this actually going to fry
the machine?

That is the point this got discussed with a colleague, who, on hearing
``five minutes per prompt,'' asked the obvious question: why not just use
something cloud-hosted instead?

Before that conversation, a local-but-not-quite-local option was briefly
on the table — spinning up a VM through Azure's student credit pack. That
idea died fast: none of the free-tier images actually came with a GPU or
VRAM attached, and getting one that did meant paying real money, which
defeats the entire point of ``free'' hardware.

The colleague's actual suggestion was AWS Bedrock~\cite{aws_bedrock},
Amazon's managed access layer for foundation models. Signing up only asks for a card to
confirm you are an actual person rather than a bot farming free credits.
No charge, and it comes with somewhere in the \$100--\$200 range of usage
credit (the exact figure depends on the offer running at the time). No
local hardware to babysit, no card actually getting charged, and access
to models far larger than anything a 4~GB GPU could ever load. That
combination made the decision an easy one.

\section{Cleaning Out the Local Stack}

Once cloud inference was clearly the model going forward, the local-model
code that had made up the entire agent through Chapter~2 turned into dead
weight rather than a fallback worth keeping around. Out went the Ollama
startup calls, the GPU-layer tuning, and the routing logic across
whichever local model happened to be loaded at the time — all of it
collapsed into a single ``call Bedrock'' path. The old code was not
deleted outright; it was moved into the project's archive as a record of
the experimentation rather than something expected to run again. The
cleanup had a practical side effect too, beyond tidiness: the server
itself started faster, since it no longer had to load a model into memory
before it could serve a single request.

\section{Making the Cloud Call Reliable}

A local model either answers or it crashes. A network call to a shared
API fails in a completely different way: throttling, timeouts, or the
odd server-side hiccup that has nothing to do with the question being
asked and everything to do with system load at that exact moment.
Treating every one of those as a hard failure would have made the agent
flaky in exactly the way switching to Bedrock was supposed to fix. So
the Bedrock call got wrapped in a retry layer instead: on a transient
error it backs off exponentially and tries again, up to four attempts,
and only retries when nothing had already streamed back so a partial
response never gets duplicated. Small piece of plumbing, but it is the
difference between the agent occasionally failing for no visible reason
and quietly recovering from the kind of hiccup any cloud API throws
from time to time.

\section*{Conclusion}
\addcontentsline{toc}{section}{Conclusion}

This chapter covered the actual move away from local inference: an 8B
model that took minutes per response and risked frying the hardware,
retired in favor of AWS Bedrock — tested first on qwen3-32b, settled into
qwen3-next-80b-a3b as the model most of the project actually ran on, with
32B kept around for when speed mattered more. Once that direction was
clear, the old local-model code was cleaned out entirely rather than kept
as a fallback, and the API call itself was hardened against the transient
failures any cloud service produces. Before getting into what the agent
built on top of this call can actually do, the next chapter covers what
it is actually working against — a database that never sits still.
